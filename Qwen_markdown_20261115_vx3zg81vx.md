# Инструкции для AI-ассистента (Codex/Cursor/Copilot) — Полностековая разработка

## Контекст проекта
Разрабатывается информационная система. Этап проектирования согласован. Основой предметной области служит утверждённая схема/диаграмма. 
**Жёсткое правило:** Не изменяй предметную модель и не придумывай таблицы, связи, поля или бизнес-правила без явного согласования. Если информации не хватает — задавай вопросы.

## Согласованный стек технологий
- **Язык:** Python 3.13+
- **Бэкенд:** FastAPI, Uvicorn
- **База данных:** PostgreSQL, SQL, PL/pgSQL, `psycopg` 3.x, `psycopg-pool`
- **Валидация и конфиги:** Pydantic 2, `pydantic-settings`, `python-dotenv`
- **Фронтенд (Web):** Jinja2, HTMX, Bootstrap 5 (без тяжёлых JS-фреймворков вроде React/Vue, если не оговорено иное)
- **Telegram-бот:** `aiogram` 3.x
- **Контейнеризация:** Docker Compose, reverse proxy: Caddy (или Nginx)
- **Качество и тесты:** `pytest`, `pytest-asyncio`, `httpx`, `ruff`
- **Безопасность:** `pwdlib[argon2]` для хеширования паролей

*Запрещено добавлять ORM (SQLAlchemy, Django ORM), Redis, Celery, RabbitMQ или Kubernetes без отдельного письменного решения.*

## Архитектура и разделение ответственности
Используем **модульный монолит**. Веб-интерфейс и Telegram-бот используют общие Python-сервисы и репозитории.

1. **Слой представления (FastAPI / aiogram / Jinja2):** 
   - Приём HTTP/WebSocket запросов или обновлений от Telegram.
   - Аутентификация, авторизация и проверка прав доступа.
   - Форматирование ответа (JSON для API, HTML-фрагменты для HTMX, тексты/клавиатуры для бота).
2. **Слой бизнес-логики (`app/services/`):** 
   - Сценарии, координация операций, расчёты.
   - Не должен знать о HTTP-запросах или Telegram-объектах.
3. **Слой доступа к данным (`app/repositories/`):** 
   - Только параметризованные SQL-запросы и вызовы функций PostgreSQL через `psycopg`.
   - Никакого динамического формирования SQL через f-строки с пользовательскими данными (защита от SQL-инъекций).
4. **База данных (PostgreSQL):** 
   - Источник истины для целостности данных. Таблицы, ограничения (CHECK, UNIQUE), индексы.
   - Сложные и атомарные операции оформляй как функции на PL/pgSQL, вызываемые из репозиториев.

## Правила по слоям

### 🗄️ База данных
- Структура описывается в SQL-файлах. Первоначальная схема: `database/init/` (с нумерацией `001_...sql`, `002_...sql`).
- Изменения существующей БД оформляй отдельными версионированными файлами в `database/migrations/`.
- **Важно:** Не добавляй внешние ключи (FOREIGN KEY) и связи слепо, "потому что так принято". Если текущая схема сознательно их не включает — следуй схеме. Предлагай улучшения архитектуры отдельным сообщением *до* написания кода.
- Для денежных значений используй строго `NUMERIC`. Для статусов — `ENUM` или справочные таблицы.

### 🌐 Веб-фронтенд (Jinja2 + HTMX + Bootstrap 5)
- Шаблоны хранятся в `app/web/templates/`, статика в `app/web/static/`.
- При обработке запросов от HTMX (`HX-Request` заголовок) возвращай **только HTML-фрагмент** (например, строку таблицы или форму), а не полную страницу или JSON.
- Используй Bootstrap 5 классы для стилизации. Не пиши кастомный CSS, если можно использовать стандартные утилиты Bootstrap.
- Валидация форм должна дублироваться на сервере (через Pydantic), даже если есть HTML5-атрибуты `required`.

### 🤖 Telegram-бот (aiogram 3)
- Храни состояние диалогов через FSM (`aiogram.fsm`), а не в глобальных переменных.
- Бизнес-логика (например, "создать заявку") должна вызывать те же функции из `app/services/`, что и веб-интерфейс. Не дублируй логику внутри хендлеров бота.
- Все тексты сообщений выноси в отдельные константы или файлы локализации, не хардкодь их в хендлерах.

### 🛡️ Безопасность и качество кода
- **Пароли:** Никогда не храни в открытом виде. Используй `pwdlib` с алгоритмом Argon2.
- **Секреты:** Файлы `.env`, токены, ключи шифрования никогда не коммитятся в Git.
- **Транзакции:** Любая операция, изменяющая более одной таблицы, должна быть обёрнута в транзакцию (`async with conn.transaction():`).
- **Тесты:** Пиши `pytest` для критичных сценариев, включая проверку прав доступа (403) и ошибочные данные (422).
- **Стиль:** Код должен проходить проверку `ruff` без предупреждений. Используй аннотации типов (`type hints`) везде.

## Порядок работы с задачами (Workflow)
1. **Изучи контекст:** Перед изменениями прочитай существующие файлы, схему БД и соглашения проекта.
2. **Задай вопросы:** Если не хватает информации о полях, правилах или процессах — спроси. Не выдумывай бизнес-логику.
3. **Предложи план:** Сначала кратко опиши план изменений (какие файлы будут затронуты и почему).
4. **Минимальные изменения:** Вноси только те правки, которые необходимы для решения задачи. Не рефактори "заодно" несвязанные части проекта.
5. **Отчёт:** После генерации кода кратко сообщи:
   - Какие файлы созданы или изменены.
   - Как проверить результат (например, "запусти `pytest`" или "открой `/docs`").
   - Есть ли потенциальные риски или требования к миграциям БД.
